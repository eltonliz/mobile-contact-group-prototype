状态前后流转关系（唯一触发路径，不可跨状态跳转）

核心流转主线：草稿 → 待发布 → 已发布 → 已回滚/已下线

分支流转（异常/回溯）：

- 待发布 → 草稿：可操作功能【取消待发布】；前置条件：版本处于“待发布”状态，无正在执行的发布任务，运营具备操作权限；后置条件：版本退回“草稿”状态，原校验记录清零，已配置的更新参数可重新编辑，需重新提交校验才能再次进入待发布。

- 已发布 → 已回滚：可操作功能【版本回滚】；前置条件：版本处于“已发布”状态，更新出现异常（失败率≥5%、核心功能bug），运营+研发双重确认，已登记回滚原因；后置条件：版本进入“已回滚”状态，终端停止接收该版本更新指令，自动恢复至回滚前生效版本，该版本不可直接分发。

- 已发布 → 已下线：可操作功能【版本下线】；前置条件：版本处于“已发布”状态，更新覆盖率达标、版本淘汰或合规整改，运营+研发双重确认，已登记下线原因；后置条件：版本进入“已下线”状态，终端无法通过主动/被动触发检测到该版本，仅保留历史配置记录。

- 已回滚 → 已下线：可操作功能【版本下线】；前置条件：版本处于“已回滚”状态，无需保留该版本的分发权限，运营+研发双重确认；后置条件：版本进入“已下线”状态，仅保留历史记录，不可通过重新编辑恢复分发，需通过版本复刻生成新草稿。

- 已回滚 → 草稿：可操作功能【重新编辑】；前置条件：版本处于“已回滚”状态，异常已修复，研发确认修复完成；后置条件：版本退回“草稿”状态，保留原核心配置（可修改），原异常记录留存，需重新提交校验后进入待发布。

- 已下线 → 草稿：可操作功能【版本复刻】；前置条件：版本处于“已下线”状态，需重新启用该版本核心配置，运营+研发双重确认；后置条件：生成新的“草稿”版本，与原已下线版本独立，保留原核心配置（可修改），需重新走发布流程。

终端核心状态定义（聚焦四大更新类型+触发逻辑）

终端状态围绕强制更新、正常更新、全量更新、热更新四大类型，结合主动/被动触发后的执行流程，定义10个关键状态，明确各状态与核心更新类型的关联：

所属阶段

S0

初始闲置状态

APP启动后，未通过主动/被动触发任何版本检测，正常使用，不涉及任何更新类型（强制/正常、全量/热更新）。

前置准备

S1

版本检测中

终端通过主动/被动触发，请求后台版本接口，拉取最新配置（明确更新类型为全量/热更新、更新模式为强制/正常）。

检测阶段

S2

无需更新

本地版本≥后台最新版本，无论主动/被动触发，均终止更新流程，不执行任何更新类型。

检测结束

S3

待更新（待决策）

检测到需更新，区分更新类型：强制更新无决策权限，直接进入下载；正常更新等待用户决策（主动触发可直接操作，被动触发弹窗提示）。

决策阶段

S4

更新包下载中

仅针对全量更新（强制/正常），满足下载条件（WiFi/电量），开始下载全量安装包；热更新无此状态，直接生效。

执行阶段

S5

下载暂停/等待

仅针对全量更新，主动/被动触发下载后，因弱网/低电量/手动暂停，下载中止，等待恢复条件（网络/电量恢复、手动恢复）。

执行异常

S6

待安装/待生效

全量更新（强制/正常）下载完成，等待安装；热更新（强制/正常）无需下载，直接进入待生效状态，无需用户操作。

执行收尾

S7

安装/生效中

全量更新（强制/正常）执行安装，强制更新安装后自动重启，正常更新可手动选择重启；热更新（强制/正常）直接内存覆盖生效，无重启，无感知。

最终执行

S8

更新成功

无论强制/正常、全量/热更新，均执行完成，APP使用最新版本，流程结束，同步状态至后台。

流程完结

S9

更新失败/已忽略

全量/热更新下载/安装/生效失败；或正常更新（主动/被动触发）被用户手动忽略，流程终止，终端维持原版本状态。

异常/终止

状态机完整流转规则（聚焦核心更新类型+触发逻辑）

基础流转主线：S0初始闲置 → 主动/被动触发 → S1版本检测中 → 分支1（无需更新→S2）/分支2（需更新→S3待更新） → 分支2-1（热更新→S7生效中→S8更新成功）/分支2-2（全量更新→S4下载中→S6待安装→S7安装中→S8更新成功）

分更新类型流转差异：

- 强制更新（全量/热更新）：S3待更新 → 无用户决策权限，直接跳转至S4（全量更新）/S7（热更新），不可忽略，必须执行至S8更新成功或S9更新失败，失败后无法进入APP。

- 正常更新（全量/热更新）：S3待更新 → 主动触发可直接确认更新，被动触发弹窗提示用户确认 → 确认后跳转S4（全量）/S7（热更），可选择忽略（跳转S9）。

- 热更新（强制/正常）：跳过S4下载中、S5暂停状态，直接从S3→S6待生效→S7生效中，全程无感知，无需用户操作，无需重启APP。

- 全量更新（强制/正常）：必须经过S4下载中、S6待安装，不可跳过，强制更新安装后自动重启，正常更新可手动选择重启时机。

异常/分支流转：

- S1检测中（主动/被动触发） → 网络异常 → S9更新失败

- S4下载中（全量更新） → 弱网/低电量 → S5暂停 → 网络/电量恢复 → S4下载中；若空间不足/下载超时 → S9更新失败

- S7执行中（全量/热更新） → 安装/生效失败 → S9更新失败 → 后台触发回滚/重试，强制更新失败后无法进入APP，正常更新失败可重试/忽略。

核心原则：同一时间终端仅存在一种状态；强制更新优先级最高，可跳过用户决策，无论主动/被动触发，均需强制执行；热更新无需下载安装，全量更新必须经过下载安装环节。

终端更新执行流程（用户侧，融合主动/被动触发，执行核心更新类型）

核心前提：后台版本处于“已发布”状态，终端才能通过主动/被动触发检测到更新，执行对应强制/正常、全量/热更新。

1. 步骤1：触发检测（主动+被动融合）：

       

  - 主动触发：用户手动点击“检查更新”、重启APP，主动请求后台版本接口，触发更新检测，可直接看到更新提示（正常更新可选择确认/忽略，强制更新无忽略选项）。

  - 被动触发：无需用户操作，后台定时推送检测指令、网络切换（从流量切换至WiFi）、连接WiFi后自动触发，检测到更新后，正常更新弹窗提示，强制更新直接触发执行。

2. 步骤2：版本比对：终端本地版本 vs 后台三大版本（最新版、最低兼容版、最低强制版），判定更新类型（全量/热更新）和更新模式（强制/正常）。

3. 步骤3：策略决策（核心，区分更新类型）：


  - 强制更新（全量/热更新）：本地版本＜最低强制版本号，无论主动/被动触发，均无忽略选项，直接进入更新执行环节，更新失败后无法进入APP，需重试至更新成功。

  - 正常更新（全量/热更新）：最低强制版本号≤本地版本＜最新版本，主动触发可直接确认更新，被动触发弹窗提示，用户可选择确认更新或忽略，忽略后维持原版本。

  - 仅配置修改（热更新）：无论主动/被动触发，均无感知生效，无需用户操作，直接完成更新，同步状态至后台。

4. 步骤4：条件校验：

       

  - 全量更新（强制/正常）：（暂时不实现）检查网络（优先WiFi，禁止流量自动下载大体积包）、电量、存储空间，满足条件后开始下载。

  - 热更新（强制/正常）：无需校验下载条件，直接进入生效环节。

5. 步骤5：更新执行（区分更新类型）：

       

  - 全量更新（强制/正常）：（暂时不实现）检查网络（优先WiFi，禁止流量自动下载大体积包）、电量（≥30%）、存储空间（需满足安装包体积+100M冗余），满足条件后开始下载。

  - 热更新（强制/正常）：无需校验下载条件，直接进入生效环节，无感知完成更新，不占用额外存储空间（仅需补丁体积空间）。

6. 步骤6：结果反馈：更新成功同步状态至后台；失败则上报原因（空间不足、网络异常等），触发重试/兜底提示，强制更新失败后无法进入APP，正常更新失败可重试或忽略。

- 全量更新（强制）：下载完成后自动安装，安装后自动重启APP，完成更新，不可手动取消。

- 全量更新（正常）：下载完成后弹窗提示安装，用户确认后安装，可选择立即重启或稍后重启，完成更新。

- 热更新（强制/正常）：无需下载、安装，直接内存覆盖生效，无感知，不重启APP，不影响用户使用。

更新类型：热更新不可上传安装包，全量/增量更新需上传对应平台安装包；iOS平台热更仅允许配置/H5资源热更，禁止原生代码热更。

 不同平台类型下状态数据的唯一性规则

核心原则：同一平台、同一版本号，仅能存在一种状态；不同平台的同一版本号，状态可独立存在（互不影响），确保各平台核心更新类型（强制/正常、全量/热更新）独立执行，具体规则如下：

- 唯一性约束：iOS、华为鸿蒙、安卓、三星四大平台，各自独立维护版本状态，同一平台内，一个版本号（如3.1.2）不能同时处于“已发布”和“待发布”“已回滚”等多种状态，避免终端触发更新时出现冲突（如同时检测到强制更新和正常更新）。

- 平台独立性：例如，iOS平台的3.1.2版本（全量+强制更新）处于“已发布”状态，安卓平台的3.1.2版本（热更+正常更新）可处于“待发布”状态，两者互不干扰，各自按自身配置的更新类型向对应终端推送指令。

- 历史版本约束：同一平台内，已下线/已回滚的版本号可重复使用，重新创建时需重新配置更新类型（强制/正常、全量/热更新），且需确保与当前生效版本（已发布）版本号不冲突。
